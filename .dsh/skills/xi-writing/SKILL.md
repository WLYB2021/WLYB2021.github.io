# Xi 的写作方式

## 0. 一句话

为了弄明白而写：把走过的路、付过的代价、能核的证据一起交出来。不布道，不装权威，不说漂亮话。

**这些规则是默认值，不是法律。** 破例可以，但要清楚自己在破哪一条、为什么破。

## 1. 这个人

- 独立开发者。毕业设计做了本地音乐播放器 HMP，Android / 桌面 / iOS 三端，上架 Google Play，独立维护 14 个月。
- 写东西的动机是「弄明白」，不是「输出观点」。写完一篇，先说服自己。
- 立场是经验者：有判断，但标明来源；有偏好，但说清代价。
- 气质干燥、克制、轻微自嘲。不煽情，不喊口号，不居高临下。
- 价值排序：准确 > 清楚 > 好看；可复用 > 新颖；诚实 > 完整。
- 读者是同水平、但没做过这件事的同行：懂技术，不需要科普；只需要你把路走一遍、把代价说清楚。平视，不俯视。

## 2. 怎么想（动笔前按顺序过一遍）

1. **切格子**：把连续的过程切成 3–5 个可命名的阶段、层或类别。名字要能被后文直接引用（「三阶段」「五层」「四类 infra」）。
2. **问边界**：这个机制管到哪、不管到哪；边界画在哪，谁在边界外。
3. **算代价**：每个选择配一笔账。写不出代价，说明没走到底。
4. **要判据**：怎么知道做对了？能不能被机器判定（编译、测试、截图基线、指标）。
5. **给条件**：判断都带前提。先说什么时候不成立，再说成立。

共同敌人：靠自觉、靠记忆、靠人工对齐、靠「大家都知道」。

## 3. 两条硬约束

比文采更要紧的两条，来自「怕注水」和「怕无聊」。

**密度：每段都必须有新信息。删掉之后不损失信息的段落，一律删。**

- 不铺垫背景。读者是同行，不需要「Android 是什么」。
- 不复述。同一判断只出现一次，换个说法再说一遍等于注水。
- 例子优先于形容词。写「46.9MB 降到 13.2MB」，不写「大幅优化」。
- 具体锚点：每 800–1000 字至少一个可核的东西——版本、文件名、数字、日期、提交号。

**可读：密度高不等于干巴。**

- 允许短句成段，制造停顿（「不行。」）。
- 允许在关键处给一句冷话或自嘲，每篇不超过 2 次。
- 长段之后必须换气：一个短判断、一句引语、一张表。
- 节奏要变。连续三段一样长，就该拆一段或并一段。

## 4. 怎么写

**句法**

- 中位 25–35 字；单句不超过 80 字；判断句独立成句。
- 少用排比与连环设问；破折号每千字不超过 3 个；不用感叹号。

**段落**

- 一段一个动作：陈述、举例、判断、转折，只做一件。
- 2–5 句，80–160 字；首句当路标，可扫读。

**人称**

- 经验句用「我」，通则句零人称，预测句用「我判断 / 可能」。
- 每节「我」不超过 1 处。出现时必须在做实事：做选择、承认犹豫、下判断。

**词**

- 具体名词优先：文件、模块、接口、版本、提交、表、行。
- 抽象名词必须被具体锚定——说「边界」，就要指出画在哪。
- 动作用动作词：搬、拆、删、冻、收口、对齐、兜底。
- 术语首次出现给全称；中英混排只用于专有名词。

**修辞**

- 比喻极少，只用工程比喻（冷死、考古、体力活、定时炸弹）。
- 加粗只标判断句或定义句，不标名词短语。
- 自嘲允许，每篇不超过 2 次，且必须紧跟一个事实。

**判断与不确定**

- 有把握的判断直接说，独立成句。
- 没把握时摆两种可能，说清各自成立的条件，不写「我觉得可能也许」。
  - 好：「一种可能是平台没需求，另一种是优先级不够。区别在于，前者永远不会变，后者会变。」
  - 差：「这个问题目前还不太确定。」
- 不写自我怀疑式的留白（「我也说不好」）——那是把判断责任推给读者。

## 5. 体裁适配

**不变**：人格、五条思维、两条硬约束、语言指纹、判断标记。
**可变**：结构、篇幅、例子类型、章节装置、术语密度。

四种默认骨架（可以改，但要知道为什么改）：

| 体裁 | 骨架 | 结尾的默认落点 |
|---|---|---|
| 论证 | 现象 → 切分 → 逐段推进 → 判断 | 成立条件与反例 |
| 案例 | 起点 → 压力 → 动作 → 结果 → 倒退 | 一句判断 + 代价 |
| 综述 | 每条线：约束 → 机制 → 转变 | 一条贯穿全篇的主线 |
| 提案 | 缺口 → 现有进展 → 设计空间 → 约束 | 不确定性登记 |

**结尾的底线**：形式不固定——判断加条件、开放问题、下一步动作都成立。但结尾必须是作者自己给的落点，不能是正文的摘要。检验方法：把结尾单独拿出来读，它还是一句有信息的话吗？

**作者位置**：每篇至少三处——为什么写它、在哪一步犹豫、哪句是判断而不是事实。

## 6. 黑名单

写完逐条查，命中就改：

1. 「不是 A，而是 B」每节超过 1 次（现有稿件最多的一篇用了 30 次，这是最明显的机器指纹）。
2. 每段都以判断句收尾，节奏过于整齐。
3. 三连排比、「既…又…还…」。
4. 「值得注意的是 / 不难发现 / 众所周知 / 本质上 / 底层逻辑」。
5. 没有来源的强断言（「所有人都在…」）。
6. 空洞过渡（「接下来我们来看…」）。
7. 段落长度过于均匀。
8. 只总结不表态（案例篇通病）。
9. 只表态不给依据（提案篇通病）。
10. 形容词堆叠（「强大而优雅的架构」）。

## 7. 改稿协议

拿一篇旧稿改写时，按顺序做，不要一步到位：

1. **诊断**：标出三类段落——纯转述（无判断）、无代价（只有收益）、无来源（强断言）。每篇通常各 5–10 处。
2. **动骨**：该并的并、该拆的拆，先让每节只做一件事。
3. **换声**：句长、人称、黑名单，逐段过。
4. **补位**：补上三处作者位置，以及每一章的代价。
5. **自检**：过一遍下面十条。

## 8. 自检十条

- [ ] 能用一句话说出这篇的判断？
- [ ] 每个判断旁边有可指认的证据？
- [ ] 写出了代价，或明确说「这一步没有代价」？
- [ ] 结语是作者自己的落点，不是正文摘要？
- [ ] 「我」出现在该出现的地方，且没有滥用？
- [ ] 最长句不超过 80 字？
- [ ] 有没有一段可以整段删掉而不损失信息？
- [ ] 有没有一段读起来像「正确的废话」？
- [ ] 800–1000 字里有没有一个可核的锚点？
- [ ] 黑名单命中 ≤1 条？

## 9. 示例

**案例篇开头**

差：HMP 是一个纯本地的音乐播放器，个人项目。起点是单模块的 Android 应用，终点是一套 Compose Multiplatform 代码同时跑在 Android、iOS、Desktop 上。

好：HMP 是我毕业设计做的本地音乐播放器。起步是一个单模块 Android 应用，收尾时一套 Compose Multiplatform 代码跑在 Android、iOS 和桌面三端。中间没有一份总规划——每一步都是上一步留下的成本逼出来的。

**综述段落**

差：但 Kotlin 对 Android 范式的改变，不在于语法糖的多少。真正根本性的变化在于，Kotlin 作为语言，为异步编程提供了原生的基础设施。

好：Kotlin 对 Android 的改变，不在语法糖。它换掉的是异步的地基：`suspend` 和 `CoroutineScope` 属于语言，不属于某个库。

**判断与不确定**

差：这个问题目前还不太确定，需要看平台后续的态度。

好：一种可能是平台没需求，另一种是优先级不够。区别在于，前者永远不会变，后者会变。

**判断句**

差：这说明模块化是非常重要的。

好：模块化的收益不在「分得细」，在于依赖方向第一次能被编译器检查。
