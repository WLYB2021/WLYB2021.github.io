> 一条被走通过的路径。三个递进的阶段，四个动作：拆模块、提逻辑、迁界面、删旧层。

<!--more-->
---

### 引子 · 三段路，四步走

这是一条**已经走通过**的路径，不是推演。

它从最常见的起点出发——一个单模块的 Android 应用；经过三步改造，抵达终点——一套 UI 代码在 Android、iOS、Desktop 上渲染。

三个阶段，依次是：

1. **单体**：单端，单模块，所有代码在一个构建单元里。
2. **模块**：单端，多模块，依赖方向显式。
3. **共享**：多端，公共部分收进共享层。

其中共享阶段内部要分两步走：**先共享逻辑层**（domain + data），**再共享 UI 层**。两步不是两个阶段，是同一阶段内的推进——先到能共享逻辑，再到能共享界面。

三次阶段跃迁 + 共享阶段内的第二步，一共是四个动作：拆模块、提逻辑、迁界面、删旧层。

本文要说的是这三个阶段**各自长什么样、为什么往下走、怎么走过去**。它不声称这是唯一的路径，甚至不声称这是最优的路径。它只声称一件事：**这条路能走通，而且每一步的踩坑都被记录下来了。**

有一个现象贯穿全程，值得先说明：**每一次迁移的动机，都不是为下一次准备的。** 拆模块是为了解决编译和解耦，与跨平台无关；共享逻辑层是因为出现了第二个端；到最后共享 UI，是因为双实现维护不动了。但回顾起来，每一步又都成了下一步的前提——**没有模块化，共享层无处安放；没有逻辑共享，UI 共享无从谈起。**

路径的连贯性不在计划里，在结果里。

---

## 第一阶段 · 单体

所有代码在一个构建单元里。这一阶段要看清的是：它为什么会走到必须拆分的那一天。

### 一 · 架构实况

#### 形态

单端应用，**一个模块**。

`settings.gradle.kts` 里只有一行：

```kotlin
include(":app")
```

所有代码——UI、业务逻辑、数据访问、平台调用——都在 `app` 这一个模块里。没有边界，只有包结构的层级。

#### 内部结构

典型的分层是"按技术分包"：

```
app/src/main/java/.../
├── ui/           Compose 页面与组件
├── viewmodel/    状态与业务编排
├── repository/   数据访问
├── database/     Room 实体与 DAO
└── network/      API 调用
```

看起来分了层，实际上**每一层的边界都是软的**：

- **逻辑长在 ViewModel 里**。业务规则、状态转换、数据拼装混在一起，没有独立的领域层。
- **数据访问没有接口**。Repository 是具体类，UI 直接依赖它，没法替换实现。
- **平台调用散落各处**。`Context`、`Intent`、系统 API 随意出现在 UI 和 ViewModel 代码中。

#### 一个诚实的评价

**在这个阶段，单体是合理的，甚至是最优的。**

项目早期功能少、变更快、只有一个人或少数几个人在写。这时候引入模块化、接口抽象、依赖注入，成本高于收益。单体让改动路径最短——需要什么就在同一处加什么。

用后来的眼光否定单体是错的。单体的问题不在"它做了错事"，而在**"它缺少了一样东西，而这个东西在项目长大后才会被需要"**。

---

### 二 · 迁移动机

#### 什么时候该动

单体不会突然变得不可用，它是**逐渐变得难受**的。有三个信号，出现时说明该考虑了：

**信号一：编译时间成为日常阻塞。**
改一行代码要等一次全量构建。构建时间从"可以忽略"变成"要盯着进度条看完"。

**信号二：出现了"没人敢动的代码"。**
某个文件几百上千行，改动它需要通读全篇。这说明**边界已经隐性存在，只是没有被显式表达出来**——所有人都知道"这块不能碰"，但代码结构上没有任何标记。

**信号三：准备引入第二套技术或第二个端。**
这时单体的限制会立刻显形——无法局部替换、无法把可复用的部分单独拿出来。

#### 关键判断

**单体的问题不是"功能太多"，而是"边界不可见"。**

功能多不是问题，模块化也不会让功能变少。真正的问题是：代码里其实**存在边界**（哪些属于数据、哪些属于业务、哪些属于界面），但这些边界只存在于开发者的脑子里，没有落到构建单元上。

模块化的本质，就是**把这些隐性边界变成显性模块**。

#### 什么时候不该动

反过来，"想迁移"不等于"该迁移"。以下信号出现时，单体该继续保留：

- **只有单端，且短期内没有第二端计划。** 共享收益为零，模块化的收益可以用别的方式（如包结构约束）部分获得。
- **业务仍在高速变化期。** 模块化要求先想清楚边界，而高速变化期边界本身还在浮动，硬拆会拆错。
- **团队没有多余的试错周期。** 拆模块会有一段"什么都得挪一遍"的过渡期，需要时间成本。

判断：**模块化是一项为"未来"做的投资，先确认未来存在。**

### 三 · 迁移方法：单体 → 模块

#### 本质

把隐性边界变成显性模块。

代码文件几乎原样移动，改的主要是**归属**——原来在同一个模块里的东西，分到不同模块去。行为不变。

#### 怎么切

两种划法：

**按技术层切**——`data` / `domain` / `player` / `ui` / `app`。适合分层清晰、各层职责稳定的项目。

**按业务域切**——`feature-player` / `feature-library` / `feature-settings`。适合业务模块之间耦合低、可以并行开发的团队。

多数项目是**混合**：先按技术层切开基础设施（data / domain），再按业务域切功能模块。

#### 一个当时看不出意义的选择：UI 要不要独立成模块

这次划分里，有一个决定**在这个阶段完全看不出价值**，但在第三阶段会变成整个路径的关键——

**把 UI 层单独拆成一个模块。**

它当时看起来只是"分层更干净"的一部分：UI 归 UI，数据归数据。没有它，模块化照样成立。但把这个模块独立出来，意味着**UI 层第一次拥有了自己的构建边界**——而这个边界，正是后面"共享 UI"要落地的位置。

可以说：**第三阶段能不能到，取决于第一阶段有没有留这道口子。**

#### 迁移手法：一次性重构

这次迁移适合**一次做完**，理由：

- 目标结构清晰（模块列表是事先定好的）
- 行为不变（只是搬家）
- 有硬反馈兜底（编译通过 + 全量回归）

三条都满足，就不需要渐进——一次切到位，边界立即清晰。

#### 具体动作

1. 在 `settings.gradle.kts` 注册新模块
2. 把文件按归属移入各模块（`git mv` 保留历史）
3. 在 `build.gradle.kts` 里声明模块间依赖，方向单向（`ui → domain → data`，不反向）
4. 更新所有 `import` 的包路径
5. 空掉的旧模块从构建图移除

#### 依赖方向

模块化真正的价值不在"拆开"，在**"依赖方向显式化"**。

一个健康的依赖方向是单向的：

```
app → ui → domain → data
```

反向依赖（data 引用 ui）在单体里可以存在（反正都在一个模块），拆开后**编译会直接失败**——这正是模块化的收益：把"不该有的依赖"从"靠自觉"变成"编译期强制"。

#### 成本提示

这次迁移的真实成本不是技术难度，是**人力时间**：所有文件要挪一遍，所有引用要改一遍，中间必然有一个"改了但还没改完"的时段，这期间应用是编不过的。

把这段过渡期安排在**没有紧急需求的窗口**里，是这次迁移唯一真正需要规划的事。

#### 本阶段该留的产物

- **模块划分方案**：为什么这么切、每层职责是什么
- **迁移执行清单**：哪些文件去哪个模块、哪些依赖要改

#### 验收

- 编译通过
- 行为不变（功能一个不少）
- 依赖方向清晰且单向

到这一步，"模块"阶段成立。但要注意：**此时的模块仍然是"单端内的模块"**——它们解决的是解耦，不是复用。真正的跨端复用要到第三阶段。

## 第二阶段 · 模块

单端内的模块化：边界显式了，但还没跨端。

### 四 · 架构实况

#### 形态

单端，**多模块**。

`settings.gradle.kts` 里是一组模块：

```kotlin
include(":app")
include(":core-data")
include(":core-domain")
include(":core-player")
include(":feature-ui")
```

每个模块是一个独立的构建单元，可以单独编译。

#### 内部结构

以"按技术层切"为例，依赖方向是单向的：

```
:app          ← 应用入口，组装一切
  ↓
:feature-ui   ← Compose 页面与组件
  ↓
:core-domain  ← 领域模型与用例
  ↓
:core-data    ← Room、Repository
```

`:core-player` 相对独立——它承载播放能力（Android 上是 Media3），依赖 domain，被 UI 层通过接口调用。

#### 分层与约束

- **UI 层**：只负责渲染与交互，不含业务规则
- **Domain 层**：领域模型 + 用例，纯 Kotlin，不依赖任何平台框架
- **Data 层**：数据访问实现（Room、网络），实现 domain 定义的接口

最有价值的一条是 **domain 层不依赖任何平台框架**。这意味着它是纯粹的业务代码——**这个性质在第三阶段会被直接利用**。

#### 这个阶段的直接收益

- **编译增量**：改一个模块，不必全量重建
- **边界清晰**：模块职责写在构建配置里，不靠口口相传
- **可独立测试**：每个模块有自己的测试源集

#### 一个隐性红利

这个阶段还有一个收益，**当时通常意识不到**：

**每一个模块边界，都是未来共享层的候选切面。**

共享层不是凭空造出来的，它是把"本来就在一起、且不含平台依赖"的代码整体挪到一个新模块。而模块化已经把这些代码**按职责聚好、按依赖排好**了。将来要共享哪部分，直接搬哪个模块即可。

模块化让"共享"从一个需要重新梳理的工程，变成一个**搬运**动作。

---

### 五 · 迁移动机

#### 什么时候该走到共享

模块化解决了"边界"，但没解决"复用"——**模块是单端内的，跨端需要的是共享层。**

两个信号说明时候到了：

**信号一：出现了第二个端。**
iOS、Desktop、Web——只要要支持多于一端，从零重写的代价就会立刻显现。

**信号二：同一份逻辑出现多份拷贝。**
即使还没正式支持第二个端，只要同一段业务逻辑被复制到第二个地方（比如先做了个桌面版原型），维护成本就已经开始计时。

#### 关键判断

**模块是单端内的，共享层是跨端的。**

这两件事没有替代关系。模块化把代码按职责分开，让每部分**可被复用**；共享层把其中的通用部分**实际复用**到多个端。前者是前提，后者是行动。

#### 分叉点：共享从哪一层开始

共享不必一次到位。第一个决定是：**先共享哪一层？**

这个问题有三个变量参与判断：

| 变量 | 含义 | 倾向共享的条件 |
|---|---|---|
| **平台耦合密度** | 该层依赖多少平台 API | 低——依赖越少越容易共享 |
| **变更频率** | 该层改动有多频繁 | 低——不变的东西共享收益稳定 |
| **一致性要求** | 各端该层是否必须一致 | 越高越值得共享（尤其"必须一致"时） |

三个变量指向同一个结论：**从"耦合最低、变更最少"的层开始。**

对一个典型的应用来说，这就是 **domain + data 层**：

- 领域模型与用例是纯逻辑，平台耦合接近零
- 数据访问虽然有平台差异（数据库驱动、文件路径），但**差异是可枚举的**——能被一个个列出来、逐个解决
- 而 UI 层恰好相反：耦合高（平台 UI 框架不同）、一致性要求复杂（移动端与桌面端交互模型本就不同）

**结论：先共享逻辑，UI 暂时各自实现。**

### 六 · 迁移方法：模块 → 共享（第一步 · 共享逻辑层）

#### 本质

**把"业务要什么"从"平台怎么做"里剥离出来。**

这一步的技术动作不是"移植代码"，而是"**定义接口**"。业务逻辑本身大多与平台无关，可以直接搬；真正要处理的，是那些"同一个业务意图在不同平台上做法不同"的地方。

#### 核心动作：定义接口，而非移植代码

剥离的方式取决于差异有没有状态：

**无状态纯逻辑 → `expect/actual`**

同一个语义，各平台算法不同。例如排序键生成、当前时间戳：

```kotlin
// commonMain
expect fun stringToPinyinSortKey(s: String): String
expect fun currentTimeMillis(): Long
```

各端提供 `actual` 实现即可。这类差异没有生命周期、没有内部状态。

**有状态的平台服务 → 接口 + 注入**

持有状态或资源的服务（如数据存储、网络客户端），不用 `expect/actual`，而是定义成接口，各端提供实现，通过依赖注入装配。

#### 平台耦合清单

从 Android 迁移到 KMP 时，需要处理的平台耦合基本逃不出这七类：

| 类别 | Android 侧 | KMP 目标 |
|---|---|---|
| 设备文件访问 | `MediaStore`、`MediaMetadataRetriever` | `expect/actual` 包一层扫描器 |
| 标签 / 元数据解析 | Jaudiotagger | `expect/actual`，各端用原生库 |
| 安全存储 | Android KeyStore | `expect/actual`，iOS 用 Keychain |
| 本地化排序 | Pinyin4j | `expect/actual`，iOS 用 `CFStringTransform` |
| 网络引擎 | OkHttp / Retrofit | Ktor Client（各端换 engine） |
| 全局上下文 | `Context` | 从签名中移除，改为构造注入 |
| 序列化 | Gson | kotlinx.serialization |

这七类里，前五类是"同一语义、各端不同实现"，中间一类是"平台概念不该进共享层"，最后一类是"换个跨平台库"。

**清单的意义**：它把"迁移"从一个开放问题，收敛成七个可逐一核对的具体项。

#### 依赖替换

除了这七类，还有一批库要从 Android 专属换成 KMP 版本：

- `androidx.room` → Room KMP（`@ConstructedBy` + `BundledSQLiteDriver`）
- `androidx.datastore` → DataStore KMP
- `Hilt` → Koin（Hilt 依赖 Android 框架，无法在 iOS 用）
- `Retrofit` → Ktor Client
- `Gson` → kotlinx.serialization

替换的原则：**尽量找官方 KMP 支持的同族库**（Room、DataStore 都是），减少重写量。

#### 迁移手法：一次性重构

这次也适合**一次做完**：

- **逻辑纯度高**：domain / data 层是纯 Kotlin，平台耦合可枚举
- **可逐层验证**：每迁一层编译一次，有硬反馈
- **行为不变**：业务逻辑的语义不因迁移而改变

但要注意一个**与后面 UI 共享的关键对比**——为什么逻辑共享能一次性重构，UI 共享不能？（这是一个可以在迁移时提前意识到的问题。）

区别在于**验证判据**：

- 逻辑层的迁移，验收标准是"**原有的测试还通过**"。逻辑有测试覆盖，行为可断言。
- UI 层的迁移，验收标准是"**界面长得对、点得动**"。这没有断言，只能靠人工对照。

**能不能一次性做完，取决于"对不对"能不能被自动判定。** 能，就一次切到位；不能，只能渐进。

#### 本阶段该留的产物

- **`expect/actual` 清单**：哪些差异用了哪种机制
- **平台耦合映射表**：每一类差异 → 用什么方案解决
- **共享接口定义**：domain 层的 Repository 接口、各端实现的分工

#### 验收

- 共享层编译通过
- 各端行为不变（功能一个不少）
- 业务逻辑在共享层**只有一份**（不是复制过来的多份）

到这一步，应用有了跨端的共享逻辑层。但 UI 仍是各端一份——这个结构就是下一阶段的起点，也是它的定时炸弹。

---

## 第三阶段 · 共享

引入第二个端，把公共部分搬进共享层。这一步内部分两段：先共享逻辑，再共享 UI。

### 七 · 架构实况：共享的两个层次

#### 共享有两种程度

"共享"不是一个终点状态，它有两种程度，差别很大：

| | 逻辑同源 | 全栈同源 |
|---|---|---|
| **共享的** | domain + data | domain + data + **UI** |
| **各端自实现的** | UI + 播放引擎 | 播放引擎 + 平台能力 |
| **UI 代码份数** | N 份 | 1 份 |
| **平台层职责** | 承载整个界面 | 只提供界面调用的能力 |

逻辑同源是**第一步**，全栈同源是**第二步**。两者都属于"共享"阶段，但形态差得远。

#### 逻辑同源：形态

```
shared/               ← domain + data，各端共用
android/app + ui/     ← Android 界面
ios/ (SwiftUI)        ← iOS 界面
desktop/ (Compose)    ← Desktop 界面
```

公共逻辑只有一份，但**界面每个端都要写一遍**。Android 写 Compose，iOS 写 SwiftUI，Desktop 可能又是另一套。

这就是"第二步"要解决的问题的来源。

#### 逻辑同源的定时炸弹

逻辑同源解决了一半问题——业务逻辑不再重复。但它留下了一个随时间恶化的结构：

**每增加一个功能，要写 N 遍 UI。**

- 加一个设置项：三端各写一遍
- 改一个交互：三端各改一遍
- 修一个界面缺陷：三端各修一遍，且可能只修了其中两端

这个成本不是线性的，是**随"端数 × 功能数"相乘增长**的。端越多、功能越密，UI 双实现的维护负担越重。

更重要的是**一致性失控**：三端的界面会逐渐分叉，同一个功能在三端长得不一样、行为不一样。要"三端体验一致"，就得在每次改动时人工对齐三处——而人工对齐是不可靠的。

#### 全栈同源：形态

```
shared/               ← domain + data
shared-ui/            ← 全部界面 + ViewModel（commonMain）
  └── platform/       ← 平台能力接口
androidMain/          ← 接口的 Android 实现
iosMain/              ← 接口的 iOS 实现（含 ObjC 桥）
desktopMain/          ← 接口的 Desktop 实现
```

界面只有一份。平台层不再承载界面，只提供**界面调用的能力**（播放引擎、分享、权限、渲染适配）。

这就是第九章要抵达的目标形态。

---

### 八 · 迁移动机：为什么必须走第二步

#### 什么时候该走

逻辑同源不会自己变成问题，它会**积累到某个点突然爆发**。信号是：

**信号一：双实现债务超过阈值。**
加一个功能，要写三遍 UI。团队开始觉得"改界面比改逻辑累得多"。

**信号二：三端开始不一致。**
同一个功能在三端表现不同，且没人能确定"哪个才是对的"。

**信号三：新功能默认只做一端。**
因为做三端太贵，团队开始有意识地"先只做 Android"，iOS 和 Desktop 慢慢落后——**产品实质上退化成了单端。**

#### 关键判断

**逻辑同源是过渡态，不是终点。**

它是一次成功的迁移，但它不是稳定的终态：只要 UI 还是 N 份，双实现成本就在持续累积。**必须提前为它的退出设定条件**——不是"哪天受不了了再说"，而是在做逻辑共享时就想清楚：UI 什么时候收成一份。

把逻辑同源当终点，就是在给未来埋一笔必然要还的债。

#### 为什么这一步最难

前两步的行为不变，只改结构。这一步不是：

- **没有"行为不变"**——界面本来就是被重写的对象
- **判据变了**——前两步验收靠"编译通过 + 测试通过"，这一步的验收是"界面长得对、点得动"，没有断言，只能人工对照
- **覆盖面最大**——整个 UI 层，几十上百个文件
- **平台差异的位置变了**——从前集中在数据层（可枚举），现在蔓延到渲染与交互层（难枚举）

判断：**这是整条路径上唯一不能靠"能编译"兜底的一步。** 方法必须不同。

### 九 · 迁移方法：共享逻辑 → 共享 UI

#### 这一步要抵达什么地方

前三步之后的应用是这样的：domain 与 data 在 `shared` 里只有一份，UI 却有三份。

共享 UI 要做的是把这三份收成一份：**所有界面代码进 commonMain，三端渲染同一套 Compose Multiplatform 代码。**

这不是"少写点 UI"，是结构性的变化：此前 UI 层是"各端各自实现"，此后 UI 层变成"共享实现 + 平台桥接"。平台代码不再承载界面，只承载界面**做不到的那部分**。

先把目标形态说清楚，再说怎么走过去。

#### 共享 UI 的形态

##### 三端跑同一套 UI，平台层剩什么

收成一份之后，收敛到最后，平台侧剩下三类：

- **播放引擎**。Android 的 Media3、iOS 的 AVFoundation、Desktop 的 FFmpeg——无法共享，也不该共享。
- **平台能力**。分享、文件选择器、权限申请、触觉反馈、悬浮窗、状态栏控制。
- **渲染层适配**。图片解码取像素、系统 insets、窗口尺寸判定。

三者的共同点：**都不产出界面，只提供界面调用的东西。**

##### 收口到两类接口

平台差异不能散落在 UI 代码里，必须收口成少数接口。

**一类是平台差异契约**，收口有状态的能力：

```kotlin
interface PlaybackController {
    val isPlaying: StateFlow<Boolean>
    val currentPosition: StateFlow<Long>
    fun play(music: MusicInfo)
    fun seekTo(positionMs: Long)
}

interface PlatformServices {
    fun share(request: ShareRequest)
    fun pickImage(onResult: (String?) -> Unit)
    suspend fun requestPermissions()
    // ...
}
```

这类接口有状态、有生命周期、实现由各端提供，通过 Koin 注入。

**另一类是纯函数式的平台差异**，用 `expect/actual`：

```kotlin
expect fun stringToPinyinSortKey(s: String): String
```

无状态、无生命周期、同一语义的两种算法——这类才用 `expect/actual`。

**分界点是状态。** 有状态的能力走"接口 + 注入"，无状态的差异走 `expect/actual`。

##### ViewModel 与状态

界面进 commonMain，ViewModel 跟着进。`androidx.lifecycle.ViewModel` KMP 化之后（`org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose`）可在 commonMain 使用，配合 `koinViewModel()` 获取实例。

分层变成：

```
UI (commonMain) → ViewModel (commonMain) → Domain (shared)
                        ↓
              平台接口（注入或 expect/actual）
```

**UI 层不再有任何直接触达平台的路径，全部经过接口。** 这是共享 UI 能成立的结构前提。

##### 两个绕不过的难点（iOS）

**跨语言状态同步。** Compose 代码编译成 Kotlin/Native 框架，Swift 侧要跨语言边界调用。commonMain 的 `PlaybackController` 持有 `StateFlow`，但 Swift 不认识它。需要一个桥：Swift 把命令送进 Kotlin 侧，Kotlin 侧把状态推给 Swift。跨边界传递复杂泛型（如 `StateFlow<MusicInfo?>`）容易踩导出名的坑——常见做法是把跨边界类型收敛到 `Any` 或 `String`。

**框架导出形态。** iOS 接入共享框架有两条路：多个 framework 或单个聚合 framework。多个静态 framework 会产生 duplicate symbol；多个动态 framework 会让 Koin 容器分裂成多个实例。常见选择是**把 shared + shared-ui 链成单个静态 framework**，CocoaPods 只引入这一个。

**平台架构裁剪。** 共享 UI 的 target 列表由依赖的构件可用性决定，不由"想支持多少架构"决定——若某依赖没有 `iosX64` 构件，就不编 `iosX64`，Intel 模拟器走 Rosetta。

#### 怎么走过去

##### 被作废的路线：并行重写

一条被真正实施过又推翻的路线：**并行重写**——新建 shared-ui，旧界面冻结为规格，逐页重写、feature flag 双轨切换。

三个问题让它塌掉：

1. **双实现并存，对齐成本相乘**。每处变更做两遍，两边还会分叉，并存页面越多交叉关系越多。
2. **资源契约被低估**。`IconKey`/`MessageKey` 到 Compose Resources 的映射、多语言键、Dimens、色值——没在开工前一次定清就边做边补、反复返工。
3. **边搬边改，两个变量叠加**。位置在变、形态也在变，出问题无法判断是搬错还是改错。

换成**迁移式提取**：先把旧界面原样搬进 shared-ui，跑起来，再整理。

##### 先定行为基线

旧界面切换后会"冷死"（从 `settings.gradle.kts` 的 include 移除，停止编译，保留源码）。冷死之后**再也无法运行时对照旧行为**。

所以切换之前必须记录：逐页截图（含浅色/深色）、截图无法表达的交互清单（手势、动效、权限流程、边界状态）。这是此后判定"有没有回归"的唯一依据——**验收标准要在改造之前就定好。**

##### 接口冻结前盘点全部调用点

`PlaybackController` / `PlatformServices` 这类接口一旦冻结，就不能再漂移。

做法是**先盘一遍旧界面里全部真实调用点**，据此一次补全，再冻结。产物是"调用点 → 接口成员"映射表——冻结后阶段内不再临时增补，有遗漏就回表登记评审。

**接口漂移是迁移失控的头号原因。**

##### 按可运行闭环推进，不做纵向切片

错误做法是按分层推进（先迁完设计系统、再组件、再页面），会制造"假完成"——底层迁完了，应用还跑不起来。

正确做法是先打通一条最小闭环：

```
入口壳 → 主页骨架 → 列表页 + 列表组件 → 播放页 + PlaybackController 接线
```

走完这四步，应用真的能用：从列表点一首歌，放出声。此后每迁一页立刻可验证。

**判据不是"迁了什么"，而是"应用此刻能不能跑"。**

##### 手法对比

| 迁移 | 手法 | 为什么 |
|---|---|---|
| 单体 → 模块 | 一次性重构 | 目标清晰、行为不变、可全量回归 |
| 模块 → 共享（逻辑） | 一次性重构 | 逻辑纯度高、有测试断言、可逐层验证 |
| 共享逻辑 → 共享 UI | **渐进式提取** | 面广、行为需人工对齐、编译兜不住 |

手法不取决于"想多彻底"，取决于"能不能被可靠验证"。

##### 迁移与整理分两阶段

第一阶段只搬，不改。允许保留旧命名、旧状态组织、旧耦合。**允许丑，不允许变。** 唯一硬性要求：剥离平台 API、补齐 `expect/actual`、替换不兼容依赖（`androidx.compose.*` → `org.jetbrains.compose.*`、Coil2 → Coil3、Hilt → Koin）。

第二阶段才整理：统一 State/Event、组件原子化、理顺资源。此时只有一份代码，不再有"两套对齐"。

价值在**锁死变量**：任何时刻只有一个变量在动。

#### 收尾最容易出的事：删除比新增危险

最后一步是删旧界面层。失败模式高度统一：**只搬走了"显示"，漏掉了"写入 / 触发"。**

界面代码有两类职责：呈现数据、把用户动作变成调用。前者显眼；后者隐蔽——藏在事件处理里，删页面时编译器拦不住，因为它调的往往是"签名还在、实现已空"的接口。

三个形态：

- **实现没搬**：新页面的"授予权限"按钮调到空壳实现，永远回调成功。界面显示已授权，功能不工作，不报错。
- **声明丢了**：能力代码完好且被调用，但**能力声明**在配置文件里被顺手动掉，且该文件由生成器维护——手动改回会被下次生成冲掉。
- **入口没搬**：界面和数据都在，唯独"添加/导入/上传"这类写入侧入口没跟过来。数据层还在后台空转，日志看不出异常。

共同特征：不让构建失败、不被测试发现，以"用户投诉"的形式延迟结算。

对治靠逐项核对：

1. **调用链回溯**——从每个界面入口查到平台实现，确认每环有真身。
2. **调用点反查**——每个平台能力反问"谁调用它"，零调用点的实现一律可疑。
3. **单源核对**——生成器产出的声明回真源核对。
4. **反向核对**——被删的东西确认"改造前是否真有人用"。

清单不产生价值，跑完才产生。

#### 本步验收

- **三端构建通过**——必要，远不充分。
- **行为基线走查**——对照切换前的截图与交互清单逐项确认。
- **能力搬迁清单跑完**——四类核对全走，重点看"写入/触发"侧。
- **旧层删除**——以上确认后从仓库移除，迁移收口。

## 复盘

### 十 · 总结：这条路径的逻辑与前提

#### 三阶段的回顾

走完这条路径，得到三个阶段的形态：

| 阶段 | 形态 | 共享边界画在哪 |
|---|---|---|
| **单体** | 单端、单模块 | 不共享 |
| **模块** | 单端、多模块 | 不共享（但边界已就位） |
| **共享** | 多端、逻辑共享 → UI 共享 | 逻辑层 → 逻辑 + UI 层 |

四个动作：**拆模块、提逻辑、迁界面、删旧层**。

#### 一条贯穿全程的线：共享边界在移动

三个阶段，本质是同一个动作做了三次：**移动共享边界。**

- 单体 → 模块：边界从"隐性"移到"显性"（虽然此时边界仍在单端内）
- 模块 → 共享：边界从"单端内"移到"跨端"
- 共享逻辑 → 共享 UI：边界从"逻辑层"移到"逻辑 + UI 层"

每一次移动，都在重新回答同一个问题：**什么该共享，什么该各自实现。**

这个问题没有一劳永逸的答案。它能被回答得越来越准，是因为每走一步，平台差异的位置就更清楚一点。

#### 三条可带走的判断

#### 判断一：边界先于共享

**没有模块化，就没有共享层的地基。**

共享层不是凭空建的，是把"本来就在一起、且不含平台依赖"的代码整体挪出来。模块化已经把这些代码按职责聚好、按依赖排好——将来要共享哪部分，直接搬哪个模块。

一个从来没做过模块化的单体，是不能直接跳到"共享"的——它缺少"可命名的边界"，迁移的第一天就是在做考古。

**推论**：如果一个团队未来"可能"跨端，**先做模块化**是近乎零后悔的选择——它的收益（解耦、编译增量）在跨端之前就已兑现，而它为跨端留下的是一道现成的口子。

#### 判断二：一次只变一个变量

**迁移与重构必须分阶段，任何时刻只有一个变量在动。**

- 第一阶段只变**位置**（搬家），不改形态
- 第二阶段只变**形态**（整理），不动位置

这条原则之所以重要，是因为**出问题时，排查范围必须是确定的**。如果位置和形态同时变，出了 bug 就无法判断是"搬错了"还是"改错了"，回归面失控。

**推论**：迁移最大的风险不是技术难度，是"两个变量同时变"。所有迁移方法论的本质，都是"把变量锁死到一次只变一个"。

#### 判断三：能不能一次做完，取决于能否被自动验证

**手法不取决于"想多彻底"，取决于"这次迁移能不能被可靠验证"。**

| 迁移 | 能自动验证吗 | 手法 |
|---|---|---|
| 单体 → 模块 | 能（编译通过 + 行为不变） | 一次性重构 |
| 模块 → 共享（逻辑） | 能（有测试断言） | 一次性重构 |
| 共享逻辑 → 共享 UI | **不能**（界面"对不对"无断言，只能人工对照） | 渐进式提取 |

前两步能一次性做完，是因为"对不对"可以被自动判定——编译过了、测试绿了，就基本对了。

第三步不能，是因为"界面对不对"没有断言。它只能靠人工对照截图与交互清单。**没有自动判据的迁移，必须渐进**，让每一步都在真实运行中被验证。

**推论**：判断一次迁移该一次性做还是渐进，先问一句——**"什么叫做对了"能不能被机器判定？** 能，就一次切到位；不能，就一步步来。

#### 可追溯的决策记录是资产

这条路径上，最有价值的产出可能不是最终的架构，而是**过程中的决策记录**。

迁移时该留下什么：

- **模块划分方案**：为什么这么切、每层职责
- **迁移执行清单**：什么去了哪里、哪些依赖改了
- **`expect/actual` 清单**：哪些差异用了哪种机制
- **平台耦合映射表**：每类差异 → 用什么方案
- **接口冻结映射表**：调用点 → 接口成员
- **迁移方案文档**：为什么选这条路、放弃了什么
- **能力搬迁检查清单**：逐项核对的结果

这些东西的价值不在"存档"，而在**"可追溯"**：当半年后有人问"为什么当时这么决定"，能拿出依据；当同类迁移再来一次，能复用而不是重新摸索。

**架构资产不只包括代码，也包括决策的来路。**

#### 这条路的前提

这条路径能走通，是有前提的：

**它成立的条件：**

- 项目确实会走向多端（哪怕只是"可能"）
- 团队有把边界画清楚的能力（或愿意先在模块化上投入）
- 迁移期能安排出"行为冻结"的窗口（尤其共享 UI 那一步）

**它不成立的条件：**

- **只有单端，且短期内没有第二端计划**——共享收益为零
- **业务处于高速变化期**——边界本身还在浮动，硬拆会拆错
- **团队没有试错周期**——每一步都需要时间来"搬家 + 验证"
- **平台重度依赖型应用**——如果应用的核心价值就在平台特性上，共享边界会被压到极薄，收益有限
- **把"代码复用率"当 KPI**——会为了共享而共享，把不该共享的东西硬塞进公共层

**跨端共享不是目标，是在特定约束下的一种选择。** 诚实地说出"什么时候不该用"，比证明"该用"更重要。

#### 迁移的隐性成本结构

如果要为这条路做预算，真正的成本在这四块：

1. **双实现并存期**——时间成本，且在共享 UI 那一步最重
2. **行为基线与验收**——需要人工逐项核对，是"人在回路"成本
3. **隐性能力倒退的追查**——返工成本，"删除比新增危险"
4. **构建与 CI 复杂化**——长期基础设施成本，多端一等公民

其中第 3 项最容易被低估，因为它**延迟结算**——以"用户投诉"的形式，在迁移完成之后才出现。

#### 结语

这条路径的价值，在于它走通过。

三个阶段、四个动作，每次迁移的动机都各不相同，但每一步都成了下一步的前提。路径的连贯性不在计划里，在结果里。

最后回到那句最该记住的话：**决定迁移成败的决策，往往发生在"决定迁移"之前。**

你有没有留出那道边界、有没有把变量锁死、有没有在建基线之前就开工——这些决定，在你正式宣布"我们要做多端架构"之前就已经做完了。

- **边界先于共享**
- **一次只变一个变量**
- **能不能一次做完，取决于能否被自动验证**
