> 一条可行路径：从单体到模块再到共享。

<!--more-->
---

## 〇 · 引子

这是一条可行路径，从最常见的起点一个单模块的 Android 应用出发，经过一步步改造抵达终点——项目的绝大多数的代码在 Android、iOS、Desktop 跨端共享。

项目全程可被划分为三个阶段，依次是：

1. **单体**：单端，单模块，所有代码在一个构建单元里。
2. **模块**：单端，多模块，依赖方向显式。
3. **共享**：多端，公共部分收进共享层。

本文主要介绍一个项目从单体单端向多模块跨端推进的过程，以及项目位于三个阶段时的状态、困境以及向下个阶段迁移的方法。

**在这种路线中，每个步骤都是稳定的。** 单体应用是小规模项目最常见的架构，模块化主要是解耦逻辑与加速编译，引入共享逻辑层可以适配第二个端，最终共享 UI 到达最终形态。你可以让你的项目停在最适合的那个状态。

---

## 一 · 单体

所有代码在一个构建单元里。UI、业务逻辑、数据访问、平台调用——都在 `app` 这一个模块里。没有边界，只有包结构的层级。

### 1-1 · 架构实况

`settings.gradle.kts` 里只有一行：

```kotlin
include(":app")
```

典型的分层是"按技术分包"：

```
app/src/main/java/.../
├── ui/           Compose 页面与组件
├── viewmodel/    状态与业务编排
├── repository/   数据访问
├── database/     Room 实体与 DAO
└── network/      API 调用
```

看起来分了层，实际上**每一层的边界都是软的**：

- **逻辑长在 ViewModel 里**。业务规则、状态转换、数据拼装混在一起，没有独立的领域层。
- **数据访问没有接口**。Repository 是具体类，UI 直接依赖它，没法替换实现。
- **平台调用散落各处**。`Context`、`Intent`、系统 API 可以随意出现在 UI 和 ViewModel 代码中。

**在项目的初期阶段，单体是合理和最优的。**

项目早期功能少、变更快、人员少。这时候引入模块化、接口抽象、依赖注入，成本高于收益。单体让改动路径最短——需要什么就在同一处加什么。单体没什么错，只是少了些东西。

---

### 1-2 · 动机

单体不会突然变得不可用，它是**逐渐变得难用**。当下面这三个信号出现时说明该考虑了模块化了：

**信号一：编译时间成为日常阻塞。**
改一行代码要等一次全量构建。构建时间从"可以忽略"变成"要盯着进度条看完"。

**信号二：出现了"没人敢动的代码"。**
某个文件几百上千行，改动它需要通读全篇。这说明**边界已经隐性存在，只是没有被显式表达出来**。

**信号三：准备引入第二套技术或第二个端。**
这时单体的限制会立刻显形——无法局部替换、无法把可复用的部分单独拿出来。

**单体的问题不是"功能太多"，而是"边界不可见"**。代码里其实存在边界（数据、业务、界面），但这些边界没有落到构建单元上。模块化的本质，就是**把这些隐性边界变成显性模块**。模块化是一种投资，前提是真的有需要。

---

### 1-3 · 单体 → 模块

模块化是把隐性边界变成显性模块，迁移时代码文件几乎原样移动，改的主要是**归属**——原来在同一个模块里的东西，分到不同模块去。行为不变。一般有两种划法：

**按技术层切**——`data` / `domain` / `player` / `ui` / `app`。适合分层清晰、各层职责稳定的项目。

**按业务域切**——`feature-player` / `feature-library` / `feature-settings`。适合业务模块之间耦合低、可以并行开发的团队。

多数项目是**混合**：先按技术层切开基础设施（data / domain），再按业务域切功能模块。

这次划分里，有一个决定**在这个阶段完全看不出价值**，但在第三阶段会变成整个路径的关键——

**把 UI 层单独拆成一个模块。**

它当时看起来只是"分层更干净"的一部分：UI 归 UI，数据归数据。没有它，模块化照样成立。但把这个模块独立出来，意味着**UI 层第一次拥有了自己的构建边界**——而这个边界，正是后面"共享 UI"要落地的位置。

#### 迁移手法：一次性重构

这次迁移适合**一次做完**，理由：

- 目标结构清晰（模块列表是事先定好的）
- 行为不变（只是搬家）
- 有硬反馈兜底（编译通过 + 全量回归）

三条都满足，就不需要渐进——一次切到位，边界立即清晰。

#### 具体动作

1. 在 `settings.gradle.kts` 注册新模块
2. 把文件按归属移入各模块（`git mv` 保留历史）
3. 在 `build.gradle.kts` 里声明模块间依赖，方向单向（`ui → domain → data`，不反向）
4. 更新所有 `import` 的包路径
5. 空掉的旧模块从构建图移除

#### 依赖方向

模块化带来的最大变化是**"依赖方向显式化"**。

一个健康的依赖方向是单向的：

```
app → ui → domain → data
```

反向依赖（data 引用 ui）在单体里可以存在（反正都在一个模块），拆开后**编译会直接失败**——这正是模块化的收益：把"不该有的依赖"从"靠自觉"变成"编译期强制"。

#### 成本提示

这次迁移的成本主要在**人力时间**，技术难度反而次要：所有文件要挪一遍，所有引用要改一遍，中间必然有一个"改了但还没改完"的时段，这期间应用是编不过的。

把这段过渡期安排在**没有紧急需求的窗口**里，是这次迁移需要规划的唯一一件事。

#### 本阶段该留的产物

- **模块划分方案**：为什么这么切、每层职责是什么
- **迁移执行清单**：哪些文件去哪个模块、哪些依赖要改

#### 验收

- 编译通过
- 行为不变（功能一个不少）
- 依赖方向清晰且单向

到这一步，"模块"阶段成立。但要注意：**此时的模块仍然是"单端内的模块"**——它们解决的是解耦，不是复用。跨端复用要到第三阶段才出现。

---

## 二 · 模块

单端内的模块化：边界显式了，但还没跨端。

### 2-1 · 架构实况

单端，**多模块**。`settings.gradle.kts` 里是一组模块：

```kotlin
include(":app")
include(":core-data")
include(":core-domain")
include(":core-player")
include(":feature-ui")
```

每个模块独立构建。依赖方向单向（按技术层切为例）：

```
:app          ← 应用入口，组装一切
  ↓
:feature-ui   ← Compose 页面与组件
  ↓
:core-domain  ← 领域模型与用例
  ↓
:core-data    ← Room、Repository
```

`:core-player` 相对独立——承载播放能力（Android 上是 Media3），依赖 domain，被 UI 层通过接口调用。

分层约束：

- **UI 层**：只负责渲染与交互，不含业务规则
- **Domain 层**：领域模型 + 用例，纯 Kotlin，不依赖任何平台框架
- **Data 层**：数据访问实现（Room、网络），实现 domain 定义的接口

**domain 层不依赖任何平台框架**——这个性质在第三阶段会被直接利用。

直接收益：编译增量、边界清晰、可独立测试。

隐性红利：**每个模块边界，都是未来共享层的候选切面**。共享层是把"本来就在一起、且不含平台依赖"的代码整体挪到新模块。模块化已经把代码按职责聚好、按依赖排好，将来要共享哪部分，直接搬哪个模块。模块化让"共享"从梳理工程变成搬运动作。

---

### 2-2 · 迁移动机

模块化解决了"边界"，但没解决"复用"——**模块是单端内的，跨端需要的是共享层。**

两个信号说明时候到了：

**信号一：出现了第二个端。**
iOS、Desktop、Web——只要支持多于一端，从零重写的代价就会立刻显现。

**信号二：同一份逻辑出现多份拷贝。**
即使还没正式支持第二个端，只要同一段业务逻辑被复制到第二个地方（比如先做了个桌面版原型），维护成本就已经开始计时。

模块化把代码按职责分开，让每部分**可被复用**；共享层把其中的通用部分**实际复用**到多个端。前者是前提，后者是行动。

共享不必一次到位。先共享哪一层，取决于三个变量：平台耦合密度（低则易共享）、变更频率（低则收益稳定）、一致性要求（越高越值得共享）。三者指向同一结论：**从耦合最低、变更最少的层开始。**

对典型应用来说，这就是 **domain + data 层**：领域模型与用例是纯逻辑，平台耦合接近零；数据访问的平台差异可枚举，逐个解决。UI 层恰好相反——耦合高、一致性要求复杂。

**结论：先共享逻辑，UI 暂时各自实现。**

---

### 2-3 · 迁移方法：模块 → 共享

这一步要做的是**把"业务要什么"从"平台怎么做"里剥离出来**。技术动作落在"定义接口"上。业务逻辑本身大多与平台无关，可以直接搬；需要处理的是"同一个业务意图在不同平台上做法不同"的地方。

剥离方式取决于差异有没有状态：

**无状态纯逻辑 → `expect/actual`**：同一语义，各平台算法不同，例如排序键生成、当前时间戳：

```kotlin
// commonMain
expect fun stringToPinyinSortKey(s: String): String
expect fun currentTimeMillis(): Long
```

**有状态的平台服务 → 接口 + 注入**：持有状态或资源的服务（如数据存储、网络客户端），定义成接口，各端提供实现，通过依赖注入装配。

从 Android 迁移到 KMP 时，平台耦合基本逃不出这七类：

| 类别 | Android 侧 | KMP 目标 |
|---|---|---|
| 设备文件访问 | `MediaStore`、`MediaMetadataRetriever` | `expect/actual` 包一层扫描器 |
| 标签 / 元数据解析 | Jaudiotagger | `expect/actual`，各端用原生库 |
| 安全存储 | Android KeyStore | `expect/actual`，iOS 用 Keychain |
| 本地化排序 | Pinyin4j | `expect/actual`，iOS 用 `CFStringTransform` |
| 网络引擎 | OkHttp / Retrofit | Ktor Client（各端换 engine） |
| 全局上下文 | `Context` | 从签名中移除，改为构造注入 |
| 序列化 | Gson | kotlinx.serialization |

前五类是"同一语义、各端不同实现"，中间一类是"平台概念不该进共享层"，最后一类是"换个跨平台库"。清单的意义：把"迁移"从开放问题收敛成七个可逐一核对的具体项。

还有一批库要从 Android 专属换成 KMP 版本：`androidx.room` → Room KMP、`androidx.datastore` → DataStore KMP、`Hilt` → Koin、`Retrofit` → Ktor Client、`Gson` → kotlinx.serialization。替换原则：**尽量找官方 KMP 支持的同族库**，减少重写量。

这次也适合**一次做完**：domain / data 层是纯 Kotlin，平台耦合可枚举，每迁一层编译一次有硬反馈，业务逻辑语义不因迁移改变。

为什么逻辑共享能一次做完，UI 共享不能？区别在于**验证判据**：逻辑层的验收标准是"原有的测试还通过"，有断言；UI 层的验收标准是"界面长得对、点得动"，只能靠人工对照。**能不能一次做完，取决于"对不对"能不能被自动判定。**

本阶段该留的产物：`expect/actual` 清单、平台耦合映射表、共享接口定义。

验收：共享层编译通过、各端行为不变、业务逻辑在共享层**只有一份**。

到这一步，应用有了跨端的共享逻辑层。但 UI 仍是各端一份——这个结构就是下一阶段的起点，也是它的定时炸弹。

---

## 三 · 共享

引入第二个端，把公共部分搬进共享层。这一步内部分两段：先共享逻辑，再共享 UI。

### 3-1 · 架构实况：共享的两个层次

"共享"不是一个终点状态，它有两种程度，差别很大：

| | 逻辑同源 | 全栈同源 |
|---|---|---|
| **共享的** | domain + data | domain + data + **UI** |
| **各端自实现的** | UI + 播放引擎 | 播放引擎 + 平台能力 |
| **UI 代码份数** | N 份 | 1 份 |
| **平台层职责** | 承载整个界面 | 只提供界面调用的能力 |

逻辑同源是第一步，全栈同源是第二步。两者都属于"共享"阶段，但形态差得远。

**逻辑同源**：

```
shared/               ← domain + data，各端共用
android/app + ui/     ← Android 界面
ios/ (SwiftUI)        ← iOS 界面
desktop/ (Compose)    ← Desktop 界面
```

公共逻辑只有一份，但界面每个端都要写一遍。这就是"第二步"要解决的问题的来源。

逻辑同源留下了一个随时间恶化的结构：**每增加一个功能，要写 N 遍 UI。** 成本随"端数 × 功能数"相乘增长，一致性也会逐渐失控——三端界面分叉，靠人工对齐是不可靠的。

**全栈同源**：

```
shared/               ← domain + data
shared-ui/            ← 全部界面 + ViewModel（commonMain）
  └── platform/       ← 平台能力接口
androidMain/          ← 接口的 Android 实现
iosMain/              ← 接口的 iOS 实现（含 ObjC 桥）
desktopMain/          ← 接口的 Desktop 实现
```

界面只有一份。平台层不再承载界面，只提供**界面调用的能力**（播放引擎、分享、权限、渲染适配）。

---

### 3-2 · 迁移动机：为什么必须走第二步

逻辑同源不会自己变成问题，它会**积累到某个点突然爆发**。三个信号：

**信号一：双实现债务超过阈值。** 加一个功能要写三遍 UI，团队开始觉得"改界面比改逻辑累得多"。

**信号二：三端开始不一致。** 同一功能在三端表现不同，且没人能确定"哪个才是对的"。

**信号三：新功能默认只做一端。** 因为做三端太贵，团队开始"先只做 Android"，iOS 和 Desktop 慢慢落后——产品实质上退化成了单端。

**逻辑同源只是过渡态。** 只要 UI 还是 N 份，双实现成本就在持续累积。必须提前设定退出条件：在做逻辑共享时就想清楚，UI 什么时候收成一份。

这一步为什么最难：前两步行为不变，只改结构。这一步没有"行为不变"——界面本来就是被重写的对象；验收判据从"编译通过 + 测试通过"变成"界面长得对、点得动"，没有断言，只能人工对照；覆盖面是整个 UI 层，几十上百个文件；平台差异从集中在数据层（可枚举）蔓延到渲染与交互层（难枚举）。**这是整条路径上唯一不能靠"能编译"兜底的一步。**

---

### 3-3 · 迁移方法：共享逻辑 → 共享 UI

目标：**所有界面代码进 commonMain，三端渲染同一套 Compose Multiplatform 代码。** UI 层从"各端各自实现"变成"共享实现 + 平台桥接"，这是结构性变化，不只是少写点 UI。平台代码不再承载界面，只承载界面做不到的那部分。

收成一份后，平台侧剩下三类：播放引擎（Android 的 Media3、iOS 的 AVFoundation、Desktop 的 FFmpeg）、平台能力（分享、文件选择器、权限申请、触觉反馈、悬浮窗、状态栏控制）、渲染层适配（图片解码取像素、系统 insets、窗口尺寸判定）。三者的共同点：**都不产出界面，只提供界面调用的东西。**

平台差异必须收口成少数接口。有状态的能力走"接口 + 注入"：

```kotlin
interface PlaybackController {
    val isPlaying: StateFlow<Boolean>
    val currentPosition: StateFlow<Long>
    fun play(music: MusicInfo)
    fun seekTo(positionMs: Long)
}

interface PlatformServices {
    fun share(request: ShareRequest)
    fun pickImage(onResult: (String?) -> Unit)
    suspend fun requestPermissions()
    // ...
}
```

无状态的差异走 `expect/actual`。**分界点是状态。**

界面进 commonMain，ViewModel 跟着进。`androidx.lifecycle.ViewModel` KMP 化后可在 commonMain 使用，配合 `koinViewModel()` 获取实例。分层变成：

```
UI (commonMain) → ViewModel (commonMain) → Domain (shared)
                        ↓
              平台接口（注入或 expect/actual）
```

**UI 层不再有任何直接触达平台的路径。** 这是共享 UI 能成立的结构前提。

iOS 的两个难点：**跨语言状态同步**——commonMain 的 `PlaybackController` 持有 `StateFlow`，Swift 不认识它，需要一个桥；跨边界传复杂泛型容易踩导出名的坑，常见做法是把跨边界类型收敛到 `Any` 或 `String`。**框架导出形态**——多个静态 framework 产生 duplicate symbol，多个动态 framework 让 Koin 容器分裂；常见选择是把 shared + shared-ui 链成单个静态 framework，CocoaPods 只引入这一个。

**被作废的路线：并行重写。** 一条被真正实施过又推翻的路线：新建 shared-ui，旧界面冻结为规格，逐页重写、feature flag 双轨切换。三个问题让它塌掉：双实现并存对齐成本相乘、资源契约（`IconKey`/`MessageKey`、多语言键、Dimens、色值）开工前没定清边做边补、边搬边改两个变量叠加出了问题无法归因。换成**迁移式提取**：先把旧界面原样搬进 shared-ui，跑起来，再整理。

**先定行为基线。** 旧界面切换后会"冷死"——从 `settings.gradle.kts` 的 include 移除，停止编译，保留源码。冷死之后再也无法运行时对照旧行为。切换之前必须记录：逐页截图（含浅色/深色）、截图无法表达的交互清单（手势、动效、权限流程、边界状态）。**验收标准要在改造之前就定好。**

**接口冻结前盘点全部调用点。** `PlaybackController` / `PlatformServices` 这类接口一旦冻结就不能漂移。做法是先盘一遍旧界面里全部真实调用点，据此一次补全，再冻结。产物是"调用点 → 接口成员"映射表。**接口漂移是迁移失控的头号原因。**

**按可运行闭环推进，不做纵向切片。** 错误做法是按分层推进（先迁完设计系统、再组件、再页面），会制造"假完成"。正确做法是先打通最小闭环：

```
入口壳 → 主页骨架 → 列表页 + 列表组件 → 播放页 + PlaybackController 接线
```

走完这四步，应用真的能用：从列表点一首歌，放出声。此后每迁一页立刻可验证。**判据是应用此刻能不能跑，跟迁了多少页无关。**

**迁移与整理分两阶段。** 第一阶段只搬不改，允许保留旧命名、旧状态组织、旧耦合，唯一硬性要求是剥离平台 API、补齐 `expect/actual`、替换不兼容依赖（`androidx.compose.*` → `org.jetbrains.compose.*`、Coil2 → Coil3、Hilt → Koin）。第二阶段才整理：统一 State/Event、组件原子化、理顺资源。价值在**锁死变量**：任何时刻只有一个变量在动。

**收尾：删除比新增危险。** 最后一步是删旧界面层，失败模式高度统一：**只搬走了"显示"，漏掉了"写入 / 触发"。** 三个典型形态：实现没搬（新页面调到空壳实现，不报错不工作）、声明丢了（能力代码完好但配置文件里的声明被顺手删掉）、入口没搬（"添加/导入/上传"这类写入侧入口没跟过来）。共同特征：不让构建失败、不被测试发现，以"用户投诉"的形式延迟结算。

对治靠逐项核对：调用链回溯（从每个入口查到平台实现，确认每环有真身）、调用点反查（每个平台能力反问"谁调用它"，零调用点一律可疑）、单源核对（生成器产出的声明回真源核对）、反向核对（被删的东西确认"改造前是否真有人用"）。清单不产生价值，跑完才产生。

验收：三端构建通过、行为基线走查（对照截图与交互清单逐项确认）、能力搬迁清单跑完（重点看写入/触发侧）、旧层删除。

## 四 · 复盘

走完这条路径，得到三个阶段的形态：

| 阶段 | 形态 | 共享边界画在哪 |
|---|---|---|
| **单体** | 单端、单模块 | 不共享 |
| **模块** | 单端、多模块 | 不共享（但边界已就位） |
| **共享** | 多端、逻辑共享 → UI 共享 | 逻辑层 → 逻辑 + UI 层 |

四个动作：**拆模块、提逻辑、迁界面、删旧层**。

三个阶段做的是同一个动作：**移动共享边界**。单体 → 模块，边界从隐性移到显性；模块 → 共享，边界从单端内移到跨端；共享逻辑 → 共享 UI，边界从逻辑层移到逻辑 + UI 层。每一次移动，都在重新回答同一个问题：什么该共享，什么该各自实现。它能被回答得越来越准，是因为每走一步，平台差异的位置就更清楚一点。

**判断一：边界先于共享。** 共享层是把"本来就在一起、且不含平台依赖"的代码整体挪出来的结果。模块化已经把代码按职责聚好、按依赖排好，将来要共享哪部分，直接搬哪个模块。一个从来没做过模块化的单体不能直接跳到"共享"——它缺少可命名的边界，迁移的第一天就是在做考古。如果一个团队未来"可能"跨端，先做模块化是近乎零后悔的选择：它的收益（解耦、编译增量）在跨端之前就已兑现，而它为跨端留下的是一道现成的口子。

**判断二：一次只变一个变量。** 任何时刻只有一个变量在动——第一阶段只变位置（搬家），不改形态；第二阶段只变形态（整理），不动位置。原因：出问题时排查范围必须是确定的。位置和形态同时变，出了 bug 就无法判断是搬错了还是改错了，回归面失控。迁移最容易出事的地方是"两个变量同时变"，跟技术难度无关。

**判断三：能不能一次做完，取决于能否被自动验证。**

| 迁移 | 能自动验证吗 | 手法 |
|---|---|---|
| 单体 → 模块 | 能（编译通过 + 行为不变） | 一次性重构 |
| 模块 → 共享（逻辑） | 能（有测试断言） | 一次性重构 |
| 共享逻辑 → 共享 UI | **不能**（界面"对不对"无断言，只能人工对照） | 渐进式提取 |

前两步能一次做完，是因为"对不对"可以被自动判定。第三步不能，只能靠人工对照截图与交互清单，必须渐进。判断一次迁移该一次性做还是渐进，看**"什么叫做对了"能不能被机器判定**。

**可追溯的决策记录是资产。** 迁移时该留下：模块划分方案（为什么这么切、每层职责）、迁移执行清单（什么去了哪里、哪些依赖改了）、`expect/actual` 清单（哪些差异用了哪种机制）、平台耦合映射表（每类差异 → 用什么方案）、接口冻结映射表（调用点 → 接口成员）、迁移方案文档（为什么选这条路、放弃了什么）、能力搬迁检查清单（逐项核对的结果）。价值在"可追溯"：半年后能拿出依据，同类迁移再来一次能复用。**架构资产不只包括代码，也包括决策的来路。**

这条路径能走通有前提。成立的条件：项目确实会走向多端（哪怕只是"可能"）、团队有把边界画清楚的能力（或愿意先在模块化上投入）、迁移期能安排出"行为冻结"的窗口（尤其共享 UI 那一步）。不成立的条件：只有单端且短期没有第二端计划（共享收益为零）、业务处于高速变化期（边界本身还在浮动，硬拆会拆错）、团队没有试错周期、平台重度依赖型应用（共享边界会被压到极薄）、把"代码复用率"当 KPI（会为了共享而共享）。**跨端共享只是特定约束下的一种选择。**

成本集中在四块：双实现并存期（时间成本，共享 UI 那一步最重）、行为基线与验收（人在回路成本）、隐性能力倒退的追查（返工成本，"删除比新增危险"）、构建与 CI 复杂化（长期基础设施成本）。其中第三项最容易被低估——以"用户投诉"的形式延迟结算。

---

这条路径的价值，在于它走通过。三个阶段、四个动作，每一步的动机都是当时的具体压力，但回头看，前一步恰好是后一步的前提。决定成败的那些选择——留出边界、锁死变量、先建基线——都发生在正式决定迁移之前。
