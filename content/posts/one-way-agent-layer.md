## 一 · 从客户端 Agent 的架构困境说起

一个本地音乐播放器的 Agent 化改造，约束只有一条：Agent 跑在应用进程内，不新起一套架构。

这条约束决定了分层。Agent 一旦和应用同进程，就必然与 UI、播放引擎、数据层共享地址空间。边界如果不显式，决策逻辑会渗进 UI，平台调用会散进业务代码。按依赖方向切三层：

| 层 | 职责 |
|---|---|
| Agent | 决策：给定上下文，产出工具调用意图 |
| Agent Runtime | 能力暴露、上下文组装、权限裁决、计量、生命周期 |
| 应用 | 领域能力与数据 |

核心循环的代码很短。端口层、工具注册与校验、上下文预算、计量、权限裁决、生命周期管理加起来，是它的几十倍。工作量集中在基建，不在决策逻辑。

分层之后，架构上做了四个决策。每个决策单独看都有理由。合在一起，走到了应用层管不到的地方。

这不是缺几个 API。API 是接口，接口背后是机制。缺的是机制。

### 决策一：Agent 常驻，被动触发，多步执行

用户说一句话，Agent 可能连续走多步。这不是一次性的问答，是一个持续数分钟的流程。

架构上的决策是让这个流程常驻。上层只有一个编排者，执行域各自持有独立的模型连接与上下文预算，由调度器按优先级启停。理由是隔离优先：某个执行域耗尽额度或端点异常，不牵连其他域。

这个决策走到系统层，撞到第一道墙：**系统的进程与服务模型按“用户操作触发的短时工作”设计，没有给常驻 Agent 留位置。** 用户在流程执行中途切到了别的应用，播放器进程被系统回收，Agent 的任务状态一起丢了。服务绑在组件上，生命周期跟着组件走，正常路径谈不上自持。只能借用既有的前台服务，把保活条件从“有音频在播”扩展为“有音频在播或 Agent 活跃”。

这件事对应系统层的**会话 infra**。

### 决策二：Agent 需要感知用户行为，才能连续决策

用户连续跳过了几首歌，对电台功能来说是一个明确信号。

架构上的决策是让 Agent 感知这类行为。调度分两条路径：一条是 ReAct 式工具循环，处理需要理解与组合的请求；另一条不进模型，本地词表直接映射到指令，毫秒级返回。分界的依据是成本结构——高频指令根本不产生 token 消耗，模型只处理模糊意图。

这个决策走到系统层，撞到第二道墙：**既有代码路径不产生信号。** 开发者的第一反应通常是写工具，实际的第一件事是可达性核查。播放器里已有的跳歌操作绕过了需要观测的位置，那些操作不产生任何信号，“连续跳过”这个感知能力从第一天起就没有输入。要么改造既有调用路径，要么在旁边接一条事件流。

这件事对应系统层的**上下文 infra**。

### 决策三：权限分档、撤销链路，设计完整

Agent 需要执行有副作用的操作，所以设计了权限分档，也设计了从审计记录到撤销的完整链路。

架构上的决策是让护栏成为 Runtime 的一部分，而不是散在业务代码里。

这个决策走到系统层，撞到第三道墙：**这类缺陷编译不过问，测试也不过问。** 权限分了几档，其中一档从设计到上线都没有任何一个工具声明使用；撤销链路设计完整，但没有接通。判断护栏是否成立，标准只有一条：改掉它，行为会不会变。没有系统层的兜底，护栏容易停在“设计完成、实现一半”。

这件事对应系统层的**治理 infra**。

### 决策四：Agent 有生命周期状态机，需要并发正确性

用户暂停了 Agent，过了一会儿又恢复。这是一个日常操作。

架构上的决策是让 Agent 的启停、暂停、恢复、回收构成一个状态机，状态机里有权责分明的并发模型。

这个决策走到系统层，撞到第四道墙：**竞态单测覆盖不到，生命周期转移需要单独构造用例。** 锁内再调停止方法会自锁；启动前等待旧循环结束，而暂停不清活跃标志，等待永不到达。“先暂停、再启动”这个日常操作，能让此后所有启停永久挂起。正确性负担全在应用侧。

这件事对应系统层的**调度 infra**。

### 四道墙后面是同一个问题

这四件事没有一件是 Agent 逻辑，全都是 Runtime 的职责。

它们还有一个共同点：**没有一件与音乐领域相关。** 一个音乐播放器和一个笔记应用的运行时需求几乎没有区别——会话该活多久、被回收时哪些状态可以丢、窗口满了先裁谁、并发状态机怎么保证正确。这些问题的答案不依赖领域知识。

客户端 Agent 的基建是重复劳动，没有共同的接口，各家实现也复用不了。

如果一组问题的答案与领域无关，它应该在哪一层被回答？

下面先看平台已经做到哪一步。

## 二 · 操作系统 AI infra 的当前进展

### 2.1 入向链路已经标准化

过去一年，主流操作系统对同一个问题给出了趋同的答案：让应用把能力声明出来，由系统建立索引，agent 发现并调用。

Android 的 [AppFunctions](https://developer.android.com/ai/appfunctions) 是最完整的形态。它是平台 API 加配套 Jetpack 库，让应用向系统注册函数供 agent 和助手调用。调用方需持有 `EXECUTE_APP_FUNCTIONS` 权限才能发现和执行。Apple 在 [WWDC26](https://developer.apple.com/wwdc26/) 正式废弃 SiriKit，[App Intents](https://developer.apple.com/app-intents/) 成为 Siri 调用第三方应用的唯一框架，新增的 App Schemas 给 Siri 预定义理解能力。HarmonyOS 的意图框架同样支持 MCP 方式接入。

四步的形状在各平台之间已经稳定：声明、索引、发现、执行。应用唯一主动的一步是声明，触发者始终是 agent 侧。入向链路已经不需要再讨论。值得讨论的，是入向之外平台还做了什么。

### 2.2 runtime 正在下沉，但下沉的是系统侧

平台开始往 runtime 层铺基建。但这些基建有一个共同的指向：**它们服务于“应用构建自己的 agent”，不是“应用向系统 agent 委派任务”。**

Google 在 2026 年 9 月发布 [ADK for Kotlin 1.0](https://google.github.io/adk-docs/)，达到与 ADK 1.0 Core 的完整功能对等，提供层级多 agent 系统、上下文压缩、human-in-the-loop 确认流、会话可恢复性，以及通过 Room 和 AppSearch 持久化 agent 状态。它降低的是应用自建 agent 的成本。

Windows 和 HarmonyOS 走得更靠近系统边界。[Microsoft Execution Containers](https://learn.microsoft.com/windows/ai/mxc) 提供策略驱动的执行层，被描述为“操作系统级的基础设施，使智能体能够在操作系统的管控下安全、持续地在后台运行”。HarmonyOS 7 的 [HMAF 2.0](https://developer.harmonyos.com/) 开放了 20 多项 AI 能力，首次释放 GUI 操控权限，应用可以 Skill 化，被系统智能体按需调度。前者管控的是 agent 在系统上的执行安全，后者做的是系统能力的 Skill 化分发。

它们让应用更容易成为 agent 的提供方或宿主，但没有给应用一个可以提交任务的出口——不是缺一个出口 API，是缺出口背后的整套 infra。

### 2.3 治理停留在准入级别

权限模型已经出现，但粒度停留在“谁能调用这个应用”。

AppFunctions 的默认访问级别允许任何持有 `EXECUTE_APP_FUNCTIONS` 权限的调用方访问，Android 框架从 17.2 开始原生强制执行访问限制。

Windows 的 MXC 在治理上走得稍远，通过 Agent 365 和 Intune 将 agent 活动连接到管理工具，让组织可以设置策略、监控风险、治理 agent。但这是企业设备管理层面的治理，不是面向普通用户的动作级授权。

授权、留痕、撤销、计量——这四件事在操作系统层面都没有出现。权限模型管的是“谁能调用”，不管“这个动作是否被用户授权”。

### 2.4 协议侧走得更远，但角色不同

协议层在出向委派上比操作系统走得更细，但它解决的是另一个层面的问题。

MCP 的 [Tasks 扩展（SEP-2663）](https://modelcontextprotocol.io/specification/2026-03-26/tasks) 定义服务器用异步任务句柄响应 `tools/call`，客户端通过轮询检索结果。它解决的是“给一个已存在的请求挂异步句柄”——先发起、稍后取，跟踪的是请求，不是接管一个目标。

[A2A Protocol v1.0](https://a2a-protocol.org/) 于 2026 年 3 月发布，引入签名 Agent Cards 用于加密验证 agent 身份。A2A 在出向委派上走得最远，但它的信任模型假设参与方身份已建立。

协议侧和操作系统是同一个故事的两面：协议解决“已经决定要委派之后怎么委派”，操作系统解决“应用能不能被发现和调用”。两者都没有触及“操作系统代表用户做授权”。

### 2.5 单向性是一个接口性质

把操作系统和协议侧的进展放在一起看，一个结构性的形状浮现出来。

平台把“应用被 agent 调用”这条链路做完整了：声明、索引、发现、执行，四步齐备，每一步都是为调用方设计的。反过来的一步没有：应用提交任务、agent 回传结果。这个接口集合的**方向性是单向的**。

权限模型的出现说明平台不是“没做治理”，而是治理停留在准入层，没有到动作层。

这个单向性不只是“少了一个 API”。API 层面的对称很容易做——加一个委派方法就行。难的是这个 API 背后的机制：任务接收面、准入判断、编排、回转、落账、撤销。这些不是接口，是 infra。

单向性引出一个自然的疑问：入向做好了，出向照着做一遍不就行了？

### 2.6 两类契约

不行。这里缺的是一类不同的契约。

入向是**函数式契约**：能力可枚举、参数有 schema、调用幂等、结果即完成。它能被标准化、被索引、被自动编排，因为每一步都能用类型和接口描述清楚。

出向需要的是**意图式契约**：目标不可枚举、需要解释、执行过程中要重新裁决、结果包含副作用而不只是返回值。

函数式契约里“执行”是一次调用，返回即结束；意图式契约里“落账”要负责副作用的可撤销性，而撤销的语义只有数据的所有者能定义。

MCP Tasks 解决的是把一次已发出的请求异步化，A2A 解决的是已经决定委派之后的对等协议。两者都没有改变契约的类型。

两类契约的差别，决定了系统层需要补的不是一个接口，而是一层 infra。原语只是这层 infra 的接口面，缺的是接口背后的机制、边界和策略框架。

下面看这层 infra 应该长什么样。

## 三 · 系统层 Agent infra 的设计

### 3.0 定义

| 名称 | 含义 |
|---|---|
| 专用 Agent | 有状态、不池化、有明确职责的系统级 Agent。记忆 Agent、审计 Agent、任务管理 Agent、助手 Agent 都属于这一类。它们的状态跨会话存活，彼此之间是横向依赖，不是上下级。 |
| 通用 Agent 池 | 无状态、池化、任务结束即释放的执行资源。池化的是执行资源，不是身份。通用 Agent 不持有跨任务的持久状态。 |
| 委派链 | 用户 → AI → 任务 → 通用 Agent → 应用能力，这条授权传递链上的每一跳都要可查、可归因、可审计。 |

还有一组关系要交代。**infra 是机制、边界和策略框架的整体；原语是 infra 的接口面。** 补几个 API 不解决问题，要补的是 API 背后的机制。

一个设计原则贯穿本章：**这层 infra 不是从零造一套新系统，而是复用现有 OS 机制的底层，在上面扩展出 Agent 所需的管理层。** 身份复用 UID 和 SELinux，会话复用前台服务和 WorkManager，发现复用 Binder 和 ContentProvider，调度复用 JobScheduler 和进程池——但每类 infra 都在这些底层机制之上新增了管理层。从零新增的只有撤销原语和推理预算。

下面走一遍任务执行链路，在链路里看每层做什么。

### 3.1 一次任务执行链路

用户在音乐播放器里说：“把刚才那几首慢歌串成一个歌单。”

**第一步：助手 Agent 接收意图。** 它判断这是一个任务，不是一次问答，把意图连同用户授权交给任务管理 Agent。

**第二步：任务管理 Agent 拆解任务。** 拆成三步：找到“刚才那几首”，创建歌单，填入曲目。它不执行任何操作，只负责编排，持有任务上下文。

**第三步：每一步分派给通用 Agent 池里的执行槽。** 池分配空闲的执行槽，把意图、上下文、授权凭证、推理预算打包投递。任务管理 Agent 持有任务上下文，每一步分派时重新打包；执行槽只执行当前这一步，不持有跨步骤状态。

**第四步：执行槽调用应用的能力。** 每一步动作在执行前经过能力边界检查、参数校验、授权裁决。应用通过 AppFunctions 声明能力，执行槽通过系统索引发现并调用。“慢歌”的语义由应用的能力提供——应用在声明“查询播放历史”这个能力时，参数里包含风格或节奏的筛选条件。

**第五步：执行中，应用推送了“用户跳了一首”的事件。** Runtime 订阅并更新上下文。上下文更新影响后续步骤的路由和组装，不回溯正在执行的步骤。

**第六步：任务完成，歌单创建成功。** 回传结果，写审计记录。

| 步骤 | 系统做什么 | 应用做什么 |
|---|---|---|
| 1 | 接收意图、判断类型 | 无 |
| 2 | 拆解任务、决定路由 | 无 |
| 3 | 分派执行槽、管理并发 | 无 |
| 4 | 能力边界检查、参数校验、授权裁决 | 执行真实操作、返回结果 |
| 5 | 接收事件、更新上下文 | 定义事件语义、推送事件 |
| 6 | 写审计、回传结果 | 定义撤销语义、响应回传 |

这条链路走完，四类 infra 都出现了。链路看起来顺，每一步底下都有硬问题——跨应用任务的原子性、委派链的撤销传播、并发冲突、上下文片段的语义一致性、提示注入防护、端侧与云侧的协同、版本演进与兼容。这些问题分散在四类 infra 中，下面逐一展开时会对应到各层。

### 3.2 架构全貌

> **[图占位：Agent 层在 Android 体系中的位置]**
>
> 展示：Agent 层插在应用框架层内，与 ActivityManager、PackageManager 同级。对外四类接口：能力注册、上下文注入、任务委派、治理接口。内部四层：专用 Agent、通用 Agent 池、Runtime 层、治理层。

刚才那条链路，走的就是这张图。

第一步和第六步发生在最上层——助手 Agent 和治理层。第二步和第三步发生在中间层——任务管理 Agent 和通用 Agent 池。第四步和第五步穿过应用框架层——执行槽调用应用能力，应用推送事件。

这张图里，Agent 层是应用框架层的一次扩展，不需要改内核、HAL 或系统库。应用只在链路两端出现：前端声明能力、贡献上下文、委派任务，后端执行能力、回传结果、定义撤销语义。中间的编排、记忆、调度、裁决、记录全部由系统完成。

### 3.3 四类 infra 机制

核心判据一句话：**当一组问题的答案与领域无关时，让每个领域各自回答一遍就是重复投入。**

**会话 infra** 解决的是“Agent 活着，但系统不知道它该活多久”的问题。系统的进程与服务模型按短时工作设计，没有给常驻 Agent 留位置。会话 infra 在复用前台服务、WorkManager 和 Binder 的基础上，新增会话管理器：会话怎么创建、状态存在哪、被回收时哪些丢哪些留。决策一的困境，答案不在应用侧。

**调度 infra** 解决的是“多个任务竞争，谁说了算”的问题。多个 Agent 同时运行，资源有限，谁先跑、跑多久、被谁抢占，应用层做不了这个仲裁。调度 infra 在复用 JobScheduler 和进程池的基础上，新增 Agent 级优先级、配额、抢占、推理预算。决策四的困境，答案不在应用侧。

**上下文 infra** 解决的是“应用有认知，但进不了决策”的问题。应用掌握用户正在听什么、口味怎么形成、最近跳过了什么，但这些只存在于应用内部。上下文 infra 在复用 ContentProvider 和 Binder 的基础上，新增注入通道、预算分配、组装策略。记忆 Agent 是上下文 infra 的内部组件，应用的片段和记忆 Agent 的记忆在 Runtime 组装时合并。这类 infra 内部的硬问题是多来源片段之间的语义一致性。决策二的困境，答案不在应用侧。

**治理 infra** 解决的是“谁授权了这个动作、出了事谁负责”的问题。动作级授权、委派链验证、审计归因、成本结算，都需要跨应用的裁决。治理 infra 在复用 Android 权限模型、SELinux 和 DevicePolicyManager 的基础上，新增逐动作授权、委派链、结构化审计、撤销原语。这类 infra 内部的硬问题是撤销传播。决策三的困境，答案不在应用侧。

**系统提供 infra，应用提供策略。** Runtime 调用记忆 Agent，记忆 Agent 决定查什么；Runtime 调用能力边界检查，权限 Agent 决定裁决依据。系统提供边界，应用决定策略。

### 3.4 上下文 infra 与认知注入

有一部分上下文只存在于应用内部。用户正在听什么、口味怎么形成、最近跳过了什么——这些不是静态字段，是从本地数据持续建模出来的结果。

缺委派接口的后果是：**决策所需的上下文与产生决策的位置分离了。** 更精确地说，缺的核心不是委派接口，是上下文 infra——它让应用在不直接参与决策的前提下，让自己的认知进入决策的输入。

这里有必要区分两类资产。一类是**能力**，应用暴露出去的工具与接口；另一类是**认知**，从本地数据持续建模出来的记忆、画像、反馈闭环。入向的设计只聚合能力，不触碰认知。但认知的价值来自参与决策：一套画像如果永远不能影响下一次推荐或下一轮编排，它就只是数据。

平台并没有主动拿走什么，**认知是因为不参与决策而贬值的。**

复用方式上，应用通过 ContentProvider 或 Binder 向 Runtime 贡献上下文片段，Runtime 在组装通用 Agent 上下文时插入。应用不直接参与决策，但它的认知参与了决策的输入。多个来源的上下文片段可能互相矛盾——应用的片段、记忆 Agent 的记忆、Runtime 自己组装的系统提示——哪个优先、怎么检测、以谁为准，是这套机制成立的前提。

### 3.5 治理：系统裁决与应用语义

治理包括四件事：授权、留痕、撤销、计量。它们有两个共同的约束。其一是**粒度**：用户授权的是“允许这个操作”，不是“允许这个应用”。其二是**范围**：一次任务可能触及多个应用的数据，任何单应用实现的授权与审计都是局部的。

但要区分裁决和语义。**治理裁决在系统层，治理语义在应用层。**

系统层负责身份、授权、跨应用审计、计量、动作级许可裁决。应用层负责领域撤销语义、数据不变量、感知事件语义、上下文建模。

撤销最能说明这个分工。系统可以记录“发生过什么”，提供撤销句柄；但回退一个副作用需要知道数据的不变量——删掉之后该恢复什么、被改过之后还能不能还原。系统可以记录，只有数据的所有者知道“怎么退回去”。

AI 权限分三层：**系统层权限**（AI 能调用哪些 OS 能力）、**应用层权限**（AI 能操作哪些应用的能力）、**AI 自身权限**（能不能主动、推理预算上限、并发任务数上限）。这三层权限的裁决都在系统层，但每层的策略来源不同：系统层和 AI 自身的默认值由 OS 厂商通过清单规定，应用层由用户运行时授予。root 或 Device Owner 可管理全部三层。这扩展了 Android 现有的三段式权限模型，但语义不同：应用权限的边界是“资源”，AI 权限的边界是“动作 + 意图 + 上下文”。

回扣第一章决策三：护栏停在设计完成，因为裁决和语义都没有归属。治理内部最难的硬问题是撤销传播——已分派的任务怎么中断、已执行的操作怎么回滚、正在排队的怎么取消，信号怎么在委派链上不遗漏、不重复、不越界地传播。

### 3.6 用户层：AI 作为特殊用户

3.5 讲了权限分几层、裁决在系统层。这一节讲这些权限怎么被携带和传递——3.1 的链路里，助手 Agent 为什么有权把任务交给任务管理 Agent？通用 Agent 为什么有权调用应用的能力？

Agent 不是直接以“用户”身份行动的，它有自己独立的 Principal。代表用户行动时，携带一条委派链：任务 ID、发起用户、授予的能力、委派的深度。每一跳都要可查、可归因、可审计。

映射到现有身份模型上：Agent 的 Principal 对应 Android 的 UID 和 SELinux 域。委派链参考 `AttributionSource` 机制——当数据流经多个应用时，系统需要知道“这个访问应该归因给谁”。

委派任务对应一个 Session，Session 绑定一组 Capability，任务结束则 Session 关闭。用户需要能撤回的不只是“整个 Agent 的授权”，还可以是某一条委派链上的某一段。许可在迁移时只能收窄，不能扩大。

### 3.7 应用侧视角

3.1 链路里应用做的六件事——声明能力、贡献领域上下文、定义撤销语义、推送感知事件、执行真实操作、响应双向通信——就是接入这套 infra 要做的全部。

应用不需要做九件事：接模型 API、管 key、实现 Agent 循环、管理会话的创建和持久化、做上下文裁剪、实现权限裁决、写审计、管计费、调度。

接入难度降低的是基建，不是语义。感知面和撤销语义无法外包，原因是语义的私有性——什么算“用户跳过了这首歌”、连续跳几首才算“不满”、删掉之后该恢复什么，这些判断依赖领域语义，系统推断不出来。

一个隐藏的代价是：接入变容易之后，应用唯一的差异化就是语义贡献的质量。基建被抽象掉之后，所有应用在能力调用这条链路上是平的，区别只在于谁知道更多领域语义、谁的撤销语义更完整、谁的感知事件更准确。**不做语义贡献的应用会迅速管道化。**

### 3.8 小结

这套设计一句话概括：**系统提供 infra，应用提供策略。**

这层 infra 解决的是第一章四道墙的问题。它不是新操作系统——Agent 层是应用框架层的扩展，底层复用 Binder、SELinux、SQLite、JobScheduler 这些既有机制，管理层是新增的。从零新增的只有撤销原语和推理预算。

本章画的是骨架。每层骨架之下都有硬问题，前面各节末尾已经点到。这些硬问题决定了骨架能不能变成可用的系统。

这层 infra 为什么还没出现在系统里，涉及责任分配和商业动力，下一章展开。

## 四 · 展望与约束

### 4.1 责任的可界定性决定落地顺序

入向和出向的落地难度，不在技术复杂度上，在责任能不能局部化。

入向的责任可以局部化。agent 调用应用声明的函数，函数内部做什么、是否正确、有无副作用，全部由应用承担。平台只提供索引与调度，边界清晰。AppFunctions 的权限模型之所以能先出来，正是因为准入控制的责任边界清楚——管住“谁能调用”就够了，调用之后的事应用自己兜着。

出向的责任无法局部化。agent 代表用户行动，一次任务可能触及多个应用的数据、产生费用、执行不可逆操作。责任主体是平台，而责任范围没有天然边界。

这不是假设。苹果在 [WWDC26 的开发者实验室](https://developer.apple.com/wwdc26/)里确认：第三方 App 无法通过任何 API 直接调用另一个 App 的意图，Siri 和快捷指令充当编排器。编排权集中在系统侧，责任也集中在系统侧。

而当 [2026 年夏天 OpenAI 与 Hugging Face 之间发生 agent 跨系统攻击事件](https://openai.com/security/)时，约 17,600 次攻击性操作在约 4.5 天的密集利用中完成，常规监控虽然捕捉到了活动，但警报没有升级为紧急响应。问题不在于检测，而在于检测到响应之间的鸿沟。没有任何单步操作会触发逐动作审核——问题出在操作的序列上，不在任何一步。

这两个事实指向同一件事：**编排权在系统侧，责任也在系统侧，而系统还没有准备好承接这个责任。** 一个歌单创建失败，是编排问题、执行问题、能力问题，还是模型判断问题？平台要回答这个问题，就需要一整套治理 infra。而这套 infra 本身还没建好。

先做责任可界定的那一侧，是工程的常规做法。

### 4.2 卖 token 的商业推力

但阻力不是全部。供需的另一侧，有一股力量往相反方向推。

[Google 的 AI Plus 计划](https://one.google.com/about/ai-plus)的价格从每月 7.99 美元降至 4.99 美元，存储翻倍到 400GB。降价不是慈善，是分发渠道的规模化策略。订阅里包含的 Daily Brief agent 能总结用户日程，Gemini Spark 则是一个 24 小时后台个人 AI agent，可在 Google 全线产品中自主完成任务。

这跟运营商卖流量是同一个结构：系统厂商不生产模型，但控制分发入口和计费通道。应用通过系统 Agent 池消耗的每一个 token，都是系统厂商的流水。[Goldman Sachs 预测](https://www.goldmansachs.com/insights/)全球 token 消耗量到 2030 年将增长 24 倍，达到每月 120 quadrillion tokens。这个市场的规模决定了平台不会停在订阅层面。

更深一层的是支付。Google 已经把 [Agent Payments Protocol（AP2）](https://ap2-protocol.org/)捐赠给 FIDO Alliance，AP2 v0.2 引入了“Human Not Present”支付——允许 AI agent 基于用户预先授权的指令独立完成购买，比如限量商品上架时立即抢购。AP2 已有超过 120 个合作伙伴，包括 PayPal。当 agent 能替用户花钱的时候，交易基础设施的归属就不再是技术问题，而是商业问题。

入向的能力声明和索引是必要的前置。出向的委派接口一旦开放，应用就能通过系统 Agent 池消耗 token，系统厂商就能卖 token。这个动力是真实的、持续的。

### 4.3 外部约束：企业与监管

推力之外，还有外部约束在拖慢节奏。

微软的 [MXC](https://learn.microsoft.com/windows/ai/mxc) 是一个观察样本。Windows 11 上的 Microsoft Execution Containers 已经正式开放，提供策略驱动的执行层，让组织定义 agent 可以访问哪些文件和网络，在运行时强制执行。但 MXC 的治理逻辑主要服务于企业场景——通过 Agent 365 和 Intune 将 agent 活动连接到管理工具，让组织设置策略、监控风险、治理 agent。这是企业设备管理层面的治理，不是面向普通用户的动作级授权。

监管是另一个约束。[EU AI Act](https://artificialintelligenceact.eu/) 的 deployer 义务已于 2026 年 8 月 2 日开始适用，要求使用高风险 AI 系统的组织保留系统生成的运营日志至少六个月，并在 15 天内向相关国家监管机构报告严重事件。不遵守的罚则最高可达 1500 万欧元或全球年收入的 3%，违反禁止性 AI 实践的罚则最高 3500 万欧元或 7%。

一个组织的合规官不会支持在结算模式和责任归属尚未清楚之前，就向第三方应用开放 agent 委派。

### 4.4 推力与阻力的对冲

商业动力和治理约束在这里是对冲的。**卖 token 的动力推动出向开放，治理的难度拖慢出向开放。**

本文判断，推力长期看会占上风——分发入口的收益是系统厂商独占的，治理成本可以随着 infra 成熟逐步摊薄。但时间尺度不确定。治理 infra 需要一整套机制被设计、实现、验证，而系统层的迭代周期以年计。

还有一个因素会拖慢节奏：出向开放之后，平台不仅承担治理责任，还承担成本风险。推理预算是有限的，如果应用可以无限制地向系统 Agent 池委派任务，谁为超出的 token 买单？结算模式没谈清楚之前，出向不会真正开放。

### 4.5 冻结错误抽象的成本

不过，平台“还没做”里面，也有“不该现在做”的成分。

可以把它表述成一个量：

> **冻结错误抽象的代价 ≈ 该层级的迭代周期 × 错误的传播范围**

协议层迭代以月计，传播范围限于采纳者，改起来是版本迁移问题。系统层迭代以年计，传播范围是整个平台上的应用，改起来是生态迁移问题。两者不在一个量级。

这解释了为什么标准自身还在调整的时候，系统层不动反而是合理的。[MCP 的任务扩展](https://modelcontextprotocol.io/specification/2026-03-26/tasks) 2025 年 10 月才立项，草案里已经把它从核心协议挪出去降为扩展。在这个阶段把它固化进操作系统，风险大于收益。

同样的逻辑适用于出向接口。如果系统层现在就把出向委派固化下来，而协议层、治理模型、结算模式都还在变，冻结的代价会被整个生态承担。**顺序比速度重要。**

### 4.6 结语

这层 infra 什么时候会有，取决于治理什么时候到位，以及商业博弈的结果。

方向是确定的：AI 已经进系统了，[AppFunctions](https://developer.android.com/ai/appfunctions)、[ADK](https://google.github.io/adk-docs/)、[Apple Intelligence](https://developer.apple.com/apple-intelligence/)、[MXC](https://learn.microsoft.com/windows/ai/mxc)、[HMAF](https://developer.harmonyos.com/) 都是信号。要让整个系统可管控地接入 AI，系统层早晚需要补这些东西。

本文提前把设计空间画出来，提供一套坐标系：运行时 infra 与运行时策略、能力边界与撤销语义、通用 Agent 与专用 Agent、入向声明与出向委派。这些区分本身就是贡献；即使平台最终选了别的实现路径，坐标系仍然有用。

形态是待定的。出向委派接口何时开放、以什么粒度开放、推理资源由谁采购和结算，取决于平台治理的进度和商业博弈的结果。推动它到来的是治理的进度，开发者的呼声作用有限；而治理到位，也不自动保证委派开放。

在那之前，应用能做的只有两件事。一是把状态变成事件、把副作用退回去，这两件在接口到来之前仍然得自己做。二是把领域语义变成可贡献的资产——这层 infra 让接入变容易，但接入变容易之后，应用唯一的差异化就是语义贡献的质量。不做语义贡献的应用会迅速管道化。

这是应用在 Agent 时代最该积累的东西。
